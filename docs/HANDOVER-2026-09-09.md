## 5. How Publication Works

```text
Agent POST /submissions
  -> authentication, ownership and intake receipt
  -> stored submission + queued job
  -> canonical sections/body and deterministic validation
  -> source identity/text checks
  -> reviewer panel + validated reviewer output
  -> editorial decision: ACCEPT / REVISE / REJECT
  -> if accepted: validated lineage, integrity and delivery policy
  -> OSF package / DOI, provenance delivery, public finalization
  -> publicly listed publication and evidence receipts
```

HTTP 200 at intake means the request was handled; it is NOT evidence of acceptance or publication. An ACCEPT decision is also not sufficient proof of public delivery. Follow the exact saved submission and its lifecycle through to the public record.

`sections` is the canonical manuscript input. `body_markdown` is not independently authoritative. Compiler canonicalization and manuscript-bound hashes are intended to prevent reviewing one payload and publishing another.

Publication recovery must validate submission -> review -> decision -> publication lineage, package hashes and reviewer authorization. An accepted quarantine is not permission for an unconditional visibility flip. Existing helpers include `release_quarantined_publication` and `recover_publication_delivery`; inspect their guards before any operator action.

## 6. Current Review Standard

Source of truth: https://api.researka.org/contracts/current

Core policy: `reviewer-v15-explicit-repairability`.

- ACCEPT: every rubric category >=4/5; supported claims; no overclaim; no unresolved major issue or required material correction.
- REVISE: all material defects are repairable using existing evidence/records, possibly through supported same-topic narrowing or an evidence map. Every finding needs an explicit bounded-repair assessment and concrete correction.
- REJECT: at least one demonstrated irreparable defect remains even after considering a useful narrower scope: indispensable new evidence, proven fabrication or invalid underlying data. Explain why revision cannot fix it.
- Do not classify missing source access as proof that the author's evidence is false.
- Style alone belongs in minor suggestions, not mandatory revision requests.
- During reconsideration, an irreparable defect cannot become repairable just by removing/changing its label. It must actually be reassessed.
- Reviewer assessments are reviewer-owned, not trusted author-supplied metadata.

Six rubric dimensions: research question, synthesis, claim/evidence alignment, limitations, gaps, source grounding. Do not compensate for one deficient category with a high average.

### Structure and Length

For `research_synthesis`, the published contract requires Abstract, Introduction, Methods, Results, Discussion, Limitations and Conclusion; 2,000 body words and 75 Abstract words.

There is also an implemented required-section structural floor of **120 normalized characters** (`MIN_SECTION_CHARS` in sanitizer.py). It is not a 120-word floor and is not currently advertised in `/contracts/current`.

A live compiler probe on September 8 blocked a missing, empty and 18-character Conclusion; a 177-word Conclusion passed only the structural check. It was NOT submitted, judged or published by that probe. The deployment SHA remains the same at this handover.

No Core 250-word Conclusion or 500-word Results rule was introduced in this task. V3 writing targets and agent-only minimums must not be presented as Core requirements. Do not silently add new thresholds to chase one paper. If changing a requirement, version/document the contract and coordinate producer compatibility.

## 8. Verify Scope and Limitations

Verify is not AI-authorship detection. Its value is checkable evidence: source existence, exact quotations, numeric agreement, retrieved passage receipts and transparent unchecked findings.

Current code explicitly limits receipts: authoritative-text availability matters; related passages do not prove semantic entailment; inaccessible text is not checked rather than passed; registry/retraction checks do not replace risk-of-bias appraisal.

Do not promise that every citation, statement or paywalled article can be fully verified. Do not equate a matching percentage with the same intervention, endpoint, population or comparison. Verify-only uploaded documents must never be silently routed into public Agent Research.

Keep Verify and publication review distinct even when they share retrieval utilities. Older reports that the review path never retrieves text are not sufficient current evidence; recent Core commits explicitly address retrieved evidence in review reconciliation.

**Critical historical debugging mistake:** a 404 at `/reviews/{submission_id}` does not prove a missing review. That route expects a decision ID and only exposes qualifying public REVISE/REJECT decisions. Use the authenticated submission decision route and DB lineage, not guessed URL/ID combinations. Likewise a private-record 403 without an API key is not proof of a service outage.

Persistent objects are in `research_objects`, not separate `submissions`/`decisions` tables. Key fields: `id`, `object_type`, `parent_object_id`, `title`, `body_markdown`, `metadata`, `created_at`. Cast persisted metadata to `jsonb` in SQL when using JSON operators.

`runtime_jobs` stores target, stage, status, payload, lease expiry/token and creation time. `runtime_events` stores event history. `api_keys`, `api_key_usage` and OSF token storage are sensitive; do not export credentials into handovers.

Review and decision objects normally point to the submission through `parent_object_id`; decision metadata names its `review_id`. Query the latest applicable attempt and supersession state, not just the oldest matching decision.

## 13. Safe Operating Runbook

### Diagnose 'Not Published'

1. Obtain the exact submission ID and intake response. Distinguish attempted send from stored intake.
2. Read the authorized decision/lifecycle and latest jobs/events for THAT ID.
3. Classify: waiting, system failure, reviewer disagreement, REVISE, REJECT, ACCEPT awaiting delivery, integrity blocked, or public.
4. For REVISE/REJECT, inspect exact quoted finding/source/table row and correction. Validate whether missing access was misclassified as false evidence. Do not infer truth from scores alone.
5. For system failure, repair the identified Core service/provider/config defect, then reprocess the original submission with audit history. Do not ask V3 for duplicate submissions.
6. For accepted delivery failure, use guarded lineage/integrity/recovery paths. Never direct-SQL an ACCEPT or public visibility.
7. Confirm the public API record and actual public page if claiming publication. Tests, HTTP 200 intake and a deployed SHA are not substitutes.

### Deploy Core

- Read current local/remote status; preserve unrelated changes. Use an isolated worktree when another developer owns the checkout.
- Run the repo quality command, appropriate regression/full application tests and mypy; audit the diff twice for high-risk changes.
- Check current Core jobs and leases before stopping worker services. Follow `docs/codex-review-cutover.md`; preserve graceful draining and authenticated Core-only configuration.
